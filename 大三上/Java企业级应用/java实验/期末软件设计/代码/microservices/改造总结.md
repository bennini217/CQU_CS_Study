# 微服务架构改造总结

## 一、改造说明

本项目是基于**实验4（management单体应用）**改造而成的**分布式微服务架构**版本。

## 二、架构对比

### 2.1 单体架构（management）

```
management/
├── controller/          # 所有控制器在一个模块
│   ├── LoginController.java
│   ├── GradeController.java
│   ├── DashboardController.java
│   ├── TeacherController.java
│   └── AIController.java
├── entity/             # 所有实体类
├── mapper/             # 所有Mapper
├── util/               # 工具类
└── StudentApplication.java  # 单一启动类
```

**特点**：
- 所有功能集中在一个应用中
- 单一端口（8080）
- 所有模块耦合在一起
- 难以独立扩展和部署

### 2.2 微服务架构（microservices）

```
microservices/
├── common/                    # 公共模块（实体类、DTO、工具类）
├── user-service/              # 用户认证服务（端口8081）
├── student-service/           # 学生服务（端口8082）
├── grade-service/             # 成绩服务（端口8083）
├── teacher-service/           # 教师服务（端口8084）
├── ai-service/                # AI服务（端口8085）
└── gateway-service/           # API网关（端口8080）
```

**特点**：
- 功能按业务领域拆分
- 每个服务独立部署、独立扩展
- 通过API网关统一入口
- 使用Nacos进行服务注册与发现
- 服务间通过OpenFeign进行通信

## 三、功能对应关系

| 单体应用（management） | 微服务架构（microservices） | 端口 |
|---------------------|------------------------|------|
| LoginController | user-service | 8081 |
| GradeController | grade-service | 8083 |
| DashboardController | grade-service | 8083 |
| TeacherController | teacher-service | 8084 |
| AIController | ai-service | 8085 |

## 四、技术栈对比

### 4.1 单体应用（management）

- Spring Boot 3.2.5
- MyBatis-Plus 3.5.5
- MySQL 8.0+
- 单一数据库连接

### 4.2 微服务架构（microservices）

**保留技术栈**：
- Spring Boot 3.2.5
- MyBatis-Plus 3.5.5
- MySQL 8.0+（所有服务共享数据库，适合演示场景）

## 五、核心改造点

### 5.1 服务拆分

按照业务领域将单体应用拆分为6个独立服务：

1. **user-service**：用户认证服务
   - 登录功能
   - 密码修改功能

2. **student-service**：学生信息服务
   - 学生信息查询
   - 学生列表查询

3. **grade-service**：成绩管理服务
   - 成绩查询
   - 成绩管理
   - 仪表盘统计

4. **teacher-service**：教师服务
   - 教师排名
   - 统计信息

5. **ai-service**：AI智能服务
   - AI问答功能

6. **gateway-service**：API网关
   - 统一API入口
   - 请求路由
   - CORS跨域处理

### 5.2 公共模块抽取

创建 `common` 模块，包含：
- 实体类（Entity）
- DTO类
- 工具类（PasswordUtil、SqlInjectionProtection等）
- 统一响应结果（Result）

所有服务都依赖 `common` 模块，保证数据模型一致性。

### 5.3 服务注册与发现

使用 **Nacos** 作为服务注册中心：
- 所有服务启动时自动注册到Nacos
- 通过服务名称进行服务发现
- 支持服务健康检查

### 5.4 API网关

使用 **Spring Cloud Gateway** 作为API网关：
- 统一入口：所有请求都通过网关（端口8080）
- 路由转发：根据路径转发到对应服务
- CORS处理：统一处理跨域请求
- 前端无需修改，仍然访问 `http://localhost:8080/api/...`

### 5.5 服务间调用

使用 **OpenFeign** 进行服务间HTTP调用：
- `grade-service` 通过Feign调用 `student-service`
- 声明式HTTP客户端，简化调用代码

## 六、数据库设计

**说明**：为了演示方便，所有微服务共享同一个数据库（`student_db`）。  
**生产环境建议**：每个服务使用独立的数据库，实现数据隔离。

## 七、配置文件变化

### 7.1 单体应用

```properties
# application.properties
server.port=8080
spring.datasource.url=...
spring.datasource.username=root
spring.datasource.password=000000
```

### 7.2 微服务架构

每个服务都有独立的 `application.yml`：

```yaml
# 服务端口（不同服务不同端口）
server:
  port: 8081

spring:
  application:
    name: user-service  # 服务名称
  datasource:
    url: jdbc:mysql://localhost:3306/student_db
    username: root
    password: "000000"
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848  # Nacos地址
```

## 八、改造优势

1. **可扩展性**：每个服务可以独立扩展，根据负载情况单独扩容
2. **可维护性**：代码按业务领域拆分，职责清晰，易于维护
3. **技术栈灵活**：不同服务可以使用不同的技术栈（目前保持一致）
4. **故障隔离**：单个服务故障不影响其他服务
5. **团队协作**：不同团队可以独立开发不同服务

## 九、改造难点与解决方案

### 9.1 服务拆分

**难点**：如何合理拆分服务？  
**解决方案**：按照业务领域（用户、学生、成绩、教师、AI）拆分。

### 9.2 数据一致性

**难点**：服务间数据如何保持一致？  
**解决方案**：目前共享数据库，生产环境建议使用分布式事务或最终一致性方案。

### 9.3 服务调用

**难点**：服务间如何调用？  
**解决方案**：使用OpenFeign进行同步HTTP调用，简单高效。

### 9.4 配置管理

**难点**：多个服务配置如何管理？  
**解决方案**：每个服务独立配置文件，生产环境建议使用Nacos配置中心。

## 十、特色功能保留

微服务架构保留了单体应用的所有特色功能：

1. **密码安全**：支持演示模式（明文）和生产模式（BCrypt加密）
2. **SQL注入防护**：所有接口都进行参数验证和SQL注入防护
3. **数据初始化**：DataInitializer自动生成测试数据（100个学生）
4. **成绩公式计算**：平时×0.1 + 期中×0.2 + 实验×0.2 + 期末×0.5
5. **AI智能问答**：AI服务提供智能问答功能
6. **仪表盘统计**：成绩走势、统计分析等功能

## 十一、后续优化建议

1. **配置中心**：使用Nacos配置中心统一管理配置
2. **服务监控**：集成Prometheus + Grafana进行服务监控
3. **分布式链路追踪**：集成SkyWalking或Zipkin
4. **数据库隔离**：每个服务使用独立数据库
5. **API版本管理**：在网关层面进行API版本控制
6. **服务限流**：在网关层面实现限流和熔断
