**二、实验原理**

### 2.1 网络分层封装与 OpenFlow 处理模型

本实验模拟了网络数据的发送与处理过程，涉及两种不同的处理模型：

1. **发送端（传统协议栈）**：采用分层封装机制，数据从应用层向下逐层添加首部信息。

   Plaintext

   ```
   应用层数据 (Payload)
        ↓ + UDP首部 (8字节)
   运输层 (UDP数据报)
        ↓ + IP首部 (20字节)
   网络层 (IP数据包)
        ↓ + MAC帧头(14字节) + FCS(4字节)
   数据链路层 (以太网帧)
   ```

2. **接收端（OpenFlow 交换机）**：不同于传统设备的逐层解包，OpenFlow 交换机采用**“解析-匹配-执行”**模型。

   - **解析 (Parsing)**：一次性读取所有头部，提取关键字段形成流特征（Flow Key）。
   - **匹配 (Matching)**：将 Key 与流表（Flow Table）比对。
   - **执行 (Action)**：根据流表指令进行转发或丢弃。

### 2.2 IP数据包结构（20字节首部）

OpenFlow 解析器需读取 IP 首部以提取 `nw_src` (源IP)、`nw_dst` (目的IP) 和 `nw_proto` (协议号)。

| **字段**          | **长度** | **说明**                     | **对应 OpenFlow 匹配域** |
| ----------------- | -------- | ---------------------------- | ------------------------ |
| **版本**          | 4 bit    | IPv4 = 4                     | -                        |
| **首部长度(IHL)** | 4 bit    | 单位4字节，通常为5（20字节） | -                        |
| **服务类型(TOS)** | 8 bit    | 服务质量                     | `nw_tos`                 |
| **总长度**        | 16 bit   | IP包总字节数                 | -                        |
| **标识**          | 16 bit   | 分片重组标识                 | -                        |
| **标志**          | 3 bit    | 分片控制                     | -                        |
| **片偏移**        | 13 bit   | 分片位置                     | -                        |
| **生存时间(TTL)** | 8 bit    | 最大跳数                     | -                        |
| **协议**          | 8 bit    | 上层协议（6=TCP，17=UDP）    | `nw_proto`               |
| **首部校验和**    | 16 bit   | 首部完整性校验 (反码求和)    | -                        |
| **源IP地址**      | 32 bit   | 发送方IP                     | `nw_src`                 |
| **目的IP地址**    | 32 bit   | 接收方IP                     | `nw_dst`                 |

### 2.3 以太网帧结构

数据链路层帧头决定了上层协议类型，是 OpenFlow 解析的起点。

| **字段**            | **长度**    | **说明**       | **对应 OpenFlow 匹配域** |
| ------------------- | ----------- | -------------- | ------------------------ |
| **目的MAC地址**     | 6字节       | 接收方网卡地址 | `dl_dst`                 |
| **源MAC地址**       | 6字节       | 发送方网卡地址 | `dl_src`                 |
| **类型/长度**       | 2字节       | 0x0800表示IPv4 | `dl_type`                |
| **数据**            | 46-1500字节 | 负载数据       | -                        |
| **帧校验序列(FCS)** | 4字节       | CRC-32校验     | -                        |

*(注：本实验通过文件模拟传输，省略了物理层的前导码和帧起始定界符)*

# 四、实验实现

本实验采用 C 语言编写，代码总量约 300 行。为了模拟真实的协议栈处理流程并实现 OpenFlow 特性，程序在内存管理、指针操作和位运算上进行了精细设计。

### 4.1 总体程序架构

程序采用单文件模块化设计，主要包含以下功能模块：

- **Packet Generator (Sender)**：模拟主机，负责构造标准的 TCP/IP 数据包。
- **OpenFlow Switch (Receiver)**：模拟交换机数据平面，负责解析与转发。
- **Controller (Control Plane)**：模拟控制器，负责初始化流表。
- **Utils**：包含 CRC32、Checksum 校验算法及 Hex Dump 可视化工具。

### 4.2 核心数据结构定义

为了实现 OpenFlow 的 10 元组匹配，首先定义了符合 OpenFlow v1.0 规范的匹配域结构体。这里展示了核心的流表项定义：



```c
/* OpenFlow 关键数据结构 */

// [OpenFlow 核心] 10元组匹配域 (Match Fields)
typedef struct {
    int ingress_port;           // 入端口
    unsigned char src_mac[6];   // 源 MAC 地址
    unsigned char dst_mac[6];   // 目的 MAC 地址
    unsigned short eth_type;    // 以太网类型 (如 0x0800)
    unsigned char src_ip[4];    // 源 IP 地址
    unsigned char dst_ip[4];    // 目的 IP 地址
    unsigned char ip_proto;     // IP 协议号 (如 17=UDP)
    unsigned short src_port;    // 源端口
    unsigned short dst_port;    // 目的端口 (关键匹配项)
    // ... 其他字段 (VLAN等)
} OpenFlowMatchKey;

// 流表项 (Flow Entry)
typedef struct {
    int is_active;              // 规则激活标志
    OpenFlowMatchKey match;     // 匹配域
    ActionType action;          // 动作 (Forward/Drop/Controller)
    int out_port;               // 转发端口
    unsigned long packet_count; // 计数器
} FlowTableEntry;
```

### 4.3 发送端：协议栈反向封装实现

为了模拟数据在内存中从高地址向低地址的“压栈”过程（类似真实的网络驱动处理），代码中使用了倒序偏移量写入数据。

**关键代码展示：**



```c
/* 网络层封装逻辑 (IPv4) */
void network_layer_init(unsigned char* buffer, IPv4_header* header, ...) { 
    // 1. 设置 IP 首部字段 (符合 RFC 791)
    header->version_ihl = 0x45;    // Version=4, IHL=5
    header->ttl = 64;              // Default TTL
    header->protocol = 17;         // UDP Protocol
    // ... (其他字段赋值)

    // 2. 计算首部校验和 (Checksum)
    // 将首部所有字段按 16 位求和并取反
    header->checksum = Checksum(checksum_buffer, 20);
```

### 4.4 工具模块：十六进制可视化 (Hex Dump)

为了直观分析二进制数据包结构，实现了一个可视化的内存转储函数。该函数**逆序遍历** buffer，将内存中的二进制流还原为人类可读的 `Header -> Payload` 顺序，并显示 ASCII 对照。

**关键代码展示：**



```c
/* 可视化十六进制输出函数 */
void print_hex_dump_visual(unsigned char* buffer, int len) {
    printf("Offset  Hex (16 bytes per line)                           ASCII\n");
    printf("------  ------------------------------------------------  ----------------\n");

    // 逆序遍历：从高地址(TotalLen)打印到低地址(0)
    for (int line_start = len - 1; line_start >= 0; line_start -= 16) {
        printf("%04X    ", offset_counter); // 打印偏移量

        // 打印十六进制部分
        for (int i = 0; i < 16; i++) {
            int idx = line_start - i;
            if (idx >= 0) printf("%02X ", buffer[idx]);
            else printf("   ");
        }
        
        // 打印 ASCII 部分 (过滤不可打印字符)
        for (int i = 0; i < 16; i++) {
            int idx = line_start - i;
            if (idx >= 0) {
                unsigned char c = buffer[idx];
                printf("%c", (c >= 32 && c <= 126) ? c : '.');
            }
        }
        printf("\n");
    }
}
```

### 4.5 接收端：OpenFlow 解析与流表匹配

这是本实验最核心的部分，模拟了 OpenFlow 交换机的数据平面流水线。与传统逐层解包不同，这里实现了**跨层解析**。

#### 4.5.1 解析器 (Parser) 实现

解析器通过指针运算，一次性定位 Ethernet、IP 和 UDP 头部，提取关键信息填入 `OpenFlowMatchKey`。



```C
void parser_extract_headers(unsigned char* buffer, int total_len, OpenFlowMatchKey* key) {
    // 1. 定位以太网头 (位于 buffer 高地址)
    int offset = total_len;
    EthernetFrame eth;
    // 提取 EtherType 用于后续判断
    memcpy(&eth.type, &buffer[offset - 14], 2);
    key->eth_type = eth.type;
    
    // 2. 解析 L3 (IP层)
    if (key->eth_type == 0x0800) { // 判断是否为 IPv4
        int ip_offset = offset - 14;
        // 提取 IP 协议号 (偏移量10)
        key->ip_proto = buffer[ip_offset - 10]; 
        
        // 3. 解析 L4 (传输层)
        if (key->ip_proto == 17) { // 判断是否为 UDP
            int udp_offset = ip_offset - 20; 
            // 提取目的端口 (关键匹配字段)
            udp_header udp;
            memcpy(&udp.dst_port, &buffer[udp_offset - 4], 2);
            
            // 将提取到的端口填入 Flow Key
            key->dst_port = udp.dst_port;
        }
    }
}
```

#### 4.5.2 流表查找与动作执行 (Lookup & Action)

模拟 TCAM (三态内容寻址存储器) 的查找行为，并在匹配成功后更新计数器并执行动作。



```c
void openflow_switch_process(unsigned char* buffer, int len) {
    // ... (调用 parser 提取 key) ...

    // 查表逻辑 (Linear Search 模拟 TCAM)
    FlowTableEntry* entry = NULL;
    for (int i = 0; i < FLOW_TABLE_SIZE; i++) {
        // 匹配逻辑：如果规则设定了 DstPort，则必须精确相等
        if (flow_table[i].match.dst_port != 0 && 
            flow_table[i].match.dst_port != key.dst_port) continue;
        
        entry = &flow_table[i]; // 匹配成功 (Hit)
        break;
    }

    // 执行动作
    if (entry != NULL) {
        printf("Match Found in Flow Table!\n");
        entry->packet_count++; // 更新统计信息
        
        if (entry->action == ACTION_FORWARD) {
            printf("[Action] FORWARD packet to Port %d\n", entry->out_port);
        }
    } else {
        printf("Table Miss. Send to Controller.\n");
    }
}
```

**六、实验总结**

### 6.1 封装/解封装与 OpenFlow 解析的对比

| **特性**     | **传统解封装 (Decapsulation)** | **OpenFlow 解析 (Parsing)**            |
| ------------ | ------------------------------ | -------------------------------------- |
| **操作方式** | 逐层剥离头部，丢弃首部信息     | 保留完整数据包，提取关键字段复制到 Key |
| **层级关系** | 严格分层 (L2 -> L3 -> L4)      | 扁平化处理 (一次性提取 10 元组)        |
| **目的**     | 获取最终的应用层数据           | 获取用于查表的匹配特征 (Flow Key)      |

### 6.2 实验收获

1. **理论与实践结合**：通过 C 语言指针对内存的直接操作，深刻体会了 RFC 文档中关于“字节序”、“偏移量”和“首部长度”定义的物理意义。
2. **可视化分析能力**：自制的 Hex Dump 工具让我能够像使用 Wireshark 一样查看内存中的原始数据，这对于调试网络协议的校验和错误（Checksum Error）非常有帮助。
3. **SDN 核心机制**：从代码层面实现了 OpenFlow 的 Match-Action 逻辑，理解了为什么 SDN 能比传统网络更灵活地控制流量（例如：可以基于 TCP 端口号在交换机层面直接丢弃数据包，实现硬件防火墙功能）。
4. **CRC32与校验和**：掌握了 CRC32 算法和反码求和算法的具体实现，验证了数据完整性校验的数学原理。
