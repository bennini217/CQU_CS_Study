# 优化方向



### 内核目前已经有哪些功能（大概能做什么）

从你给的代码来看，这个 lab9 的内核，已经具备一个「简化版 RTOS」的基本功能，主要包括：

- 启动与基础框架

- main.c 里完成：中断控制器 GIC 初始化、定时器初始化、任务模块初始化、信号量模块初始化、UART 初始化，然后启动调度器 OsActivate()，创建 idle 任务并进入多任务运行。

- 任务管理（线程）

- 任务控制块 TCB（struct TagTskCb）、任务创建/挂起/恢复等接口（PRT_TaskCreate / PRT_TaskResume / PRT_TaskSuspend / PRT_TaskDelete 等在 prt_task.h 里声明，在 prt_task_init.c 里实现）。

- 为任务分配独立的栈空间，并初始化上下文，让任务第一次运行时像「刚从中断返回」一样开始执行：

- 栈分配：OsTskMemAlloc() + 你自己简化版的 OsMemAllocAlign()（用静态数组 stackMem[20][4096] 做 20 个 4K 栈）。

- 上下文初始化：OsTskContextInit() 根据 ARMv8 的寄存器布局填好 struct TskContext。

- 维护一个「空闲 TCB 链表」g_tskCbFreeList，用 OsTskAMPInit() 一次性分配一个 TCB 数组，然后挂到空闲链表里，后续创建任务时从链表取一个 TCB。

- Idle 任务：OsTskIdleBgd() + OsIdleTskAMPCreate()，保证系统始终有任务在跑。

- 调度器（kernel/sched/prt_sched_single.c）

- 使用一个全局运行队列 g_runQueue（被你简化成单链表）保存 所有就绪任务。

- 每次调度通过 OsTskHighestSet() 遍历 g_runQueue，选出优先级数值最小的任务作为 g_highestTask。

- OsTskSchedule()：当有任务变 ready，判断是否需要切换，如果需要，设置标志位再通过 OsTaskTrap() 触发真正的上下文切换。

- OsMainSchedule() / OsFirstTimeSwitch()：真正做「RUNNING_TASK 切换 + 恢复上下文」。

- 信号量（kernel/sem/prt_sem.c）

- 实现了计数型/二进制信号量：

- PRT_SemPend()：P 操作，如果有资源就立刻拿走；否则把当前任务挂到该信号量的等待队列，然后调度走。

- PRT_SemPost()：V 操作，如果有人在等，就唤醒等待队列中第一个任务；否则增加计数。

- 支持按优先级或 FIFO 方式挂接等待队列（semMode 字段决定）。

- 有基础的错误检查和边界检查（句柄范围、溢出、在中断中 pend 等）。

- Tick 时钟与时间

- prt_tick.c：

- OsTickDispatcher()：处理每次时钟中断，g_uniTicks++，并重新设置下一次中断周期。

- PRT_TickGetCount()：对外提供当前 tick 计数（时间基准）。

- 定时器中断在 prt_exc.c 里的 OsHwiHandleActive() 中处理：IRQ 号为 30 时调用 OsTickDispatcher()。

- 中断与异常处理（bsp/prt_exc.c）

- 统一中断入口 OsHwiDispatch()：从 GIC 读中断号，分发给 OsHwiHandleActive()，处理完后再清中断。

- 封装了开关中断接口 PRT_HwiLock / PRT_HwiUnLock / PRT_HwiRestore，供内核关键区使用。

- 异常处理 + 简易系统调用框架：

- OsExcHandleFromLowElEntry()：当从低特权级触发异常（比如 SVC）时，这里解析 ESR 寄存器中的异常类型，如果是 SVC 指令，就从 x8 里取系统调用号，从 x0 里取参数，然后用 switch (syscall_num) 分发，目前只实现了一个 MyFirstSyscall()（输出字符串）。

- Shell 交互（kernel/shell/shmsg.c）

- 通过 UART + 信号量 sem_uart_rx 实现一个非常简陋的命令行：

- shell 任务 ShellTask 持续等待用户输入，每个字符来自 shellCB->shellBuf，通过 PRT_SemPend 同步。

- 支持命令：

- top：调用 OsDisplayTasksInfo() 输出当前所有任务的 PID、优先级、栈大小。

- tick：调用 OsDisplayCurTick() 输出当前 tick 值。

- 段属性与 ARMv8 相关封装

- os_attr_armv8_external.h：通过 OS_SEC_TEXT / OS_SEC_DATA / OS_SEC_BSS / OS_SEC_L4_TEXT 等宏，将不同类型/阶段的代码和数据放入不同的段，为后续性能和内存布局优化做准备。

- os_cpu_armv8.h：定义任务上下文结构、屏障指令宏（PRT_DSB/DMB/ISB）、中断掩码等。

### 可以考虑的优化方向（从易到难，逐步做）

下面我按“你是内核新手”来排个梯度，方便你一步一步做创新和优化。

#### 一、调度器与任务管理方向

1. 调度算法优化（当前是“遍历链表 O(N)”）

- 现状：OsTskHighestSet() 每次都遍历 g_runQueue 找优先级最小的任务，任务多时开销线性。

- 可以做：

- 使用「位图 + 多链表」的经典 RTOS 调度算法：对于 0~63 优先级，每个优先级一个就绪链表 + 一个 64bit 位图，通过硬件指令 CLZ/CTZ 一下找到最高优先级，复杂度 O(1)。

- 或者简化版：按优先级分成若干段，先选段再线性遍历。

1. 时间片轮转（当前没有真正的 time slice）

- 现状：同优先级任务间没有“时间片轮转”，谁先 ready 谁一直占着，除非主动阻塞。

- 可以做：

- 在 tick 中断 OsTickDispatcher() 里，给当前任务减一个 time-slice 计数，减到 0 时，把它从就绪队列尾部重排，并重置计数，实现「同优先级轮流执行」。

1. 更灵活的任务栈管理

- 现状：用静态数组 stackMem[20][4096]，最多 20 个任务，固定 4KB 栈，且简单用数组标记。

- 可以做：

- 改成真正的内存管理（比如简单的 buddy 或 partition），栈大小允许多种值；

- 或者保留静态数组，但做一个更正规的小 allocator（空闲链表、合并、释放等），支持任务删除后栈空间回收。

1. 栈溢出检测与栈使用率统计

- 结合 struct TskInfo 里已有的 currUsed / peakUsed / ovf 字段，实现在任务栈初始化时填充魔数（OS_TSK_STACK_MAGIC），定期扫描栈使用情况，支持在 shell 中加一个命令 stack 查看各任务的栈占用。

#### 二、信号量 & 同步原语方向

1. 支持真正的超时等待

- 现状：PRT_SemPend(timeout) 里如果 timeout != OS_WAIT_FOREVER，直接返回 OS_ERRNO_SEM_FUNC_NOT_SUPPORT。

- 可以做：

- 把超时等待的任务挂到一个「按到期 tick 排序」的延时链表 g_tskSortedDelay（已经有基础结构声明）；

- 在 OsTickDispatcher() 或相关定时器扫描逻辑里，检查哪个任务到期，把它们从信号量等待队列摘出来，改成超时状态并重新 ready。

1. 优先级反转问题（互斥量 & 优先级继承）

- 现状：只实现了普通信号量，没有互斥量的“优先级继承”功能。

- 可以做：

- 基于现有二值信号量，增加一个 MUTEX 类型，记录 owner；

- 当高优先级任务阻塞在某个互斥量上时，提高持有者的优先级到较高值，避免优先级反转。

#### 三、Tick 与节能方向

1. tick 处理开销优化

- 现状：OsTickDispatcher() 每次中断都加锁、加 1、重装计数器，逻辑简单但锁粒度比较粗。

- 可以做：

- 把「tick++」改成原子操作或尽量减小关中断区域；

- 后续如果实现了延时链表，可以考虑把一些工作挪到软中断或专门的扫描任务里。

1. Tickless 模式（更难一点）

- 如果未来你有兴趣，可以尝试 tickless：根据下一个超时时间设定硬件计时器周期，而不是固定 1ms；这样在任务很空闲时可以大幅降低中断频率。

#### 四、中断 / 系统调用方向

1. 中断分派表 & 通用注册接口

- 现状：OsHwiHandleActive 里用 switch(irqNum) 手写分发。

- 可以做：

- 实现一个 OsHwiCreate(irqNum, callback)，维护一个 irqHandlers[NR_IRQ] 数组，OsHwiHandleActive 里只需查数组并调用，结构更清晰，也方便将来扩展更多中断源。

1. 系统调用表 & 用户 API

- 现状：OsExcHandleFromLowElEntry() 只支持 syscall_num == 1，且直接写在 switch 里。

- 可以做：

- 和中断类似，做一个 syscall_table[NR_SYSCALL] 函数指针数组，svc 入口只负责解析号并跳表调用；

- 在用户态提供一个小的封装函数，比如 int my_write(char *buf)，内部发 svc，让实验更像“真正的内核”。

#### 五、Shell & 可观测性方向（比较容易出效果）

1. 扩展 Shell 命令

- 在 ShellTask 里增加更多命令，比如：

- ps：输出任务 PID/优先级/状态；

- stack：输出栈使用情况（结合上面的栈监控）；

- sem：输出信号量状态（当前计数、等待任务数）；

- sysinfo：输出 tick、任务数、内存使用等。

1. 调试与 Trace

- 给任务切换点、信号量 pend/post 等关键路径加上简单的 trace 记录（写到一个环形缓冲区），然后通过 shell 命令打印 recent trace，这样利于你调试和展示“创新点”。

#### 六、代码结构与可配置性方向

1. 把你做的简化改动做成「可配置项」

- 比如：

- 目前你把 TagOsRunQue 简化成 TagListObject，可以通过宏开关控制：#ifdef SIMPLE_RUNQUEUE；

- 栈分配使用固定 20 x 4K 的静态数组，也可以通过配置项选择“静态栈池模式”或“动态内存模式”。

1. 更细粒度的段属性使用

- 现在很多函数都标成 OS_SEC_TEXT，可以：

- 把非常频繁调用的函数（调度关键路径、中断关键路径）标为 OS_SEC_L0_TEXT；

- 把只在初始化期间调用的函数标为 OS_SEC_L4_TEXT，放在 .os.init.text，以后可以在镜像布局上做优化。
